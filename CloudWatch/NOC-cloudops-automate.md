# HTTPD Alarm Configuration

## Overview

The HTTPD CloudWatch Alarm is the **P1 – Critical** monitoring and auto-remediation component of the CloudOps NOC Automation project.

Its purpose is to detect an Apache HTTP Server (`httpd`) failure on the Amazon EC2 instance and initiate the automated incident-response workflow.

The alarm monitors the configured HTTPD process metric generated by the CloudWatch Agent. When the metric indicates that the Apache process is no longer running, the alarm changes to the **ALARM** state and publishes an event to the project's Amazon SNS topic.

The SNS event invokes the AWS Lambda automation function, which uses AWS Systems Manager Run Command to restart Apache on the affected EC2 instance.

---

# 1. Severity

| Property | Configuration |
|---|---|
| Severity | **P1 – Critical** |
| Service | Apache HTTP Server (`httpd`) |
| Failure Type | Apache process/service unavailable |
| Monitoring Service | Amazon CloudWatch |
| Metric Source | CloudWatch Agent |
| Notification | Amazon SNS |
| Automation | AWS Lambda |
| Remediation | AWS Systems Manager Run Command |
| Target | Amazon EC2 |

P1 represents the **critical service-availability failure** in this project.

---

# 2. Purpose

The HTTPD alarm is designed to:

- Detect Apache process failure.
- Generate a critical incident condition.
- Notify the NOC administrator.
- Trigger automated remediation.
- Restart Apache without manual SSH intervention.
- Reduce service downtime.
- Allow CloudWatch to monitor the recovery state.

# 4. Alarm Condition

The alarm evaluates the HTTPD process metric collected by the CloudWatch Agent.

Conceptually:

```text
HTTPD process running
        │
        ▼
Metric value = 1
        │
        ▼
CloudWatch Alarm = OK
```

If Apache stops:

```text
HTTPD process stopped
        │
        ▼
Metric value = 0
        │
        ▼
CloudWatch Alarm = ALARM
```

The exact metric name, namespace, dimensions, threshold, period, and evaluation settings must match the configuration deployed in the AWS environment.

```text
  │
  ▼
CloudWatch metric received
  │
  ▼
Alarm condition is normal

  ▼
```

# 7. Failure State

When Apache stops:

```text
Apache
  │
  ▼
HTTPD process unavailable
  │
  ▼
CloudWatch metric indicates failure
  │
  ▼
Alarm condition satisfied
  │
  ▼
P1 Alarm = ALARM
```

The alarm action then publishes the event to SNS.

---

# 8. Automated Remediation Workflow

After the P1 alarm enters the ALARM state:

### Step 1 – Detection

CloudWatch detects that the configured HTTPD failure condition has occurred.

### Step 2 – Alarm

The HTTPD alarm changes from:

```text
OK
```

to:

```text
ALARM
```

### Step 3 – SNS Notification

CloudWatch publishes the alarm event to the configured SNS topic.

### Step 4 – Lambda Invocation

SNS invokes the:

```text
Cloudops-NOC-automate
```

Lambda function.

### Step 5 – SSM Command

Lambda calls AWS Systems Manager Run Command.

### Step 6 – Apache Recovery

SSM Agent executes the configured Linux remediation command on EC2.

Conceptually:

```bash
sudo systemctl restart httpd
```

### Step 7 – Verification

Apache service status is checked after remediation.

Expected result:

```text
active (running)
```

### Step 8 – Monitoring Recovery

CloudWatch receives the recovered metric state and the alarm can return to:

```text
OK
```

---

# 9. Manual Failure Simulation

The P1 workflow can be tested by stopping Apache on the EC2 instance:

```bash
sudo systemctl stop httpd
```

Verify the failure:

```bash
sudo systemctl status httpd
```

Expected state:

```text
inactive
```

You can also verify the process directly:

```bash
pgrep -x httpd
```

If no HTTPD process is returned, Apache is not running.




Verify:

- SNS topic exists.
- Lambda subscription is present.
- Email subscription is confirmed.
- CloudWatch alarm action points to the correct SNS topic.

# 13. IAM Dependencies

The P1 workflow depends on appropriate IAM permissions.

### EC2 Role

The EC2 instance requires the permissions necessary for Systems Manager management, commonly provided through:

```text
AmazonSSMManagedInstanceCore
```

### Lambda Role

Lambda requires permissions to perform the required Systems Manager operations and write execution logs.

The deployed project should use the project's documented least-privilege policy rather than unnecessarily granting broad permissions.

---

# 14. Important Design Principle

The CloudWatch alarm is responsible for **detection**.

SNS is responsible for **event distribution**.

Lambda is responsible for **automation/orchestration**.

Systems Manager is responsible for **remote command execution**.

EC2/Linux is responsible for **executing the actual Apache service operation**.

Therefore:

```text
Detection ≠ Remediation
```

The services have separate responsibilities.
